--- Contenu livré (ADR 0029 phases 3–4 + ADR 0031 (a)–(g) ;

(A) V-F3 — BUDGETS D'OCTETS (ADR 0029 phase 3, exécution ADR 0011
  point 2). Le cache de PARSE (arbres résolus) gagne un budget
  d'octets ESTIMÉS (défaut 8 Mio ; coût par entrée = source retenue ×
  facteur d'arbre ESTIMÉ ×6 + enveloppe — estimation de GESTION, pas
  une mesure : le tas réel reste l'affaire du banc mémoire, R5) ;
  l'éviction LRU s'applique AU-DELÀ du budget, EN PLUS de la borne
  d'entrées (8). GARDE ANTI-CYCLAGE : l'entrée la plus RÉCENTE est
  toujours retenue — un fichier unique plus gros que le budget vit
  seul jusqu'à la suivante (jamais de put/éviction en boucle). Le
  MÉMO de localisation (verdicts fqcn → jar, fiche 024 — les verdicts
  ne périment JAMAIS par conception) gagne 2 Mio estimés : les
  NÉGATIFS sont évincés d'abord (un re-probe honnête re-sonde les
  tables centrales, le verdict rendu reste EXACT), et si le budget
  reste dépassé le mémo est vidé ENTIÈREMENT (robinet intégral, rare,
  documenté). Contrats observables fiche 024 INCHANGÉS (deux find
  successifs répondent le même verdict — seul le COÛT du re-probe
  revient). Kill-switch commun :
  jo.codeide.lsp.java.memoire.budgets.disabled=true (budget infini —
  comportement d'avant V-F3).

(B) V-F3 — SHIM onTrimMemory (ADR 0029 phase 3, exécution ADR 0011
  point 5, écart G-033). L'hôte Android traduit son
  ComponentCallbacks2.onTrimMemory(level) en
  MoteurJava.pressionMemoire(niveau) AVEC LE MÊME ENTIER — les
  constantes NiveauxPressionMemoire (5/10/15/20/40/60/80) sont le
  MIROIR de la plateforme (identité, pas traduction). Politique
  CUMULATIVE : RUNNING_*/UI_HIDDEN → les arbres résolus du cache de
  parse SEULS (le mémo de diagnose reste — la frappe reste servie au
  chemin chaud) ; BACKGROUND/MODERATE → + les mémos de diagnose ET
  les négatifs de localisation (les positifs gardent leurs handles
  ouverts) ; COMPLETE → libération INTÉGRALE par dispose drainé sous
  le verrou de compilation (le moteur reste UTILISABLE, tout se
  reconstruit paresseusement). Le signal ne paie JAMAIS la
  construction de l'environnement de noms (jrt/jars). RAPPORT
  CHIFFRÉ RapportPressionMemoire (entrées parse libérées, mémos,
  négatifs, libération intégrale — l'observable des logs appareil
  « caches d'arbre libérés » devient une DONNÉE côté hôte) et relais
  MULTI-MODULES EnvironnementCompilation.pressionMemoire (UN appel
  par signal, tous les moteurs vivants touchés). Niveau INCONNU :
  servi sans exception (< 20 → le plus doux ; ≥ 80 → intégral).
  Kill-switch : jo.codeide.lsp.java.memoire.ontrim.disabled=true.

(C) V-F4 — PLAGE PRIORITAIRE (ADR 0029 phase 4, « zone visible

  offsets ABSOLUS, même convention que CibleSuperRpc ; la DERNIÈRE

  d'envoi = comportement d'avant V-F4 à l'identique — contrats du
  cahier intacts, une salve = une publication). SONDE
  serviraitPasseComplete PUREMENT LEXICALE (lecture du mémo + preuve
  de confinement — jamais d'arbre, jamais de verrou) : le
  publicateur ne paie la double publication QUE quand la passe à
  venir serait COMPLÈTE (ouverture de grand fichier, édition
  structurelle). PASSE PRIORITAIRE diagnosePrioritaire : la source
  est MASQUÉE hors du corps VISIBLE (mécanique isomorphe au
  diagnose rapide, fiche 014), le hors-corps et le corps hôte restent
  INTACTS ; elle est PURE (aucune écriture — ni mémo ni cache de
  parse : un diagnostic partiel ne devient JAMAIS la source de
  portage d'une passe rapide suivante) ; la publication COMPLÈTE
  suit dans le MÊME tir et FAIT FOI (fil unique : l'ordre d'arrivée

  honnêtes (null → publication complète directe) : fichier sous le
  seuil, accolades déséquilibrées, offset visible hors de tout

(G) V-G (d) — willRenameFiles (écart G-022). Annonce
  workspace.fileOperations willRename + didRename sur **/*.java. Le
  geste « renommer/déplacer un .java » de l'arbre éditeur reçoit
  AVANT le renommage effectif les éditions qui gardent le projet
  cohérent : la DÉCLARATION DE PAQUET du fichier déplacé (le FQCN
  change — la plage couvre le NOM seul) et les IMPORTS de ses
  porteurs (import demo.A;, import demo.A.Imbrique;, import static
  demo.A.CHAMP; — le SEGMENT FQCN seul est réécrit, le mot-clé et le
  suffixe restent). Source fraîche de chaque porteur : le TAMPON
  OUVERT si le document l'est, le DISQUE sinon (illisible → écarté
  honnêtement). Réponse TOUJOURS un WorkspaceEdit (VIDE honnête si
  le FQCN est conservé — casse, déplacement intra-paquet — ou si le
  fichier est hors racines). didRenameFiles invalide la présence
  source et l'index de mots (le FQCN a changé). PÉRIMÈTRE HONNÊTE :
  les usages QUALIFIÉS complets SANS import (demo.A a = …) ne sont
  PAS réécrits — le cas doré de la décision est « package +
  imports » (documenté USAGE §7.26).

--- Pièges mesurés et consignés --------------------------------------

 1. L'encodage LSP 3.17 des jetons sémantiques : la COLONNE relative
    est comptée depuis le DÉBUT du jeton PRÉCÉDENT sur la même ligne
    (pas depuis sa fin) — le décodage du banc le vérifie jeton par
    jeton avant d'interroger le texte.
 2. Le champ data d'un CompletionItem revient du fil comme JsonObject
    Gson (PAS un Map) — lu par SON API (get/isJsonPrimitive/asString),
    jamais par un cast.
 3. La création du jeton workDoneProgress est une REQUÊTE
    serveur→client (le client peut refuser) — createProgress borné
    (2 s) et la progression retombe au silence sans toucher le
    préchauffage.
 4. La plage du lien relatedInformation vit dans le MÊME document que
    le diagnostic (l'URI du porteur est passée à la conversion — sans
    URI, pas de relatedInformation du tout : conversions internes
    honnêtes).
 5. Un renommage qui CONSERVE le FQCN (casse, déplacement
    intra-paquet) ne doit rien réécrire — l'edit VIDE est la bonne
    réponse, jamais une réécriture inutile.
 6. La politique de pression mémoire est en paliers par ENTIERS
    reçus (pas d'énumération fermée) : un niveau INCONNU reste servi
    (< 20 → doux, ≥ 80 → intégral) — les constantes Android peuvent
    évoluer sans casser le moteur.
 7. Le budget d'octets du cache de parse EST une estimation de
    gestion (source × 6) — le facteur est recalibrable par le banc
    mémoire qui mesure le tas RÉEL (ADR 0011/0016) ; la borne
    d'entrées RESTE (les deux se cumulent).
